# Creating a Flyway migration

This project uses **Flyway** for SQL-first migrations. The ORM (Spring Data JDBC) does **not** generate or alter schema. Every schema change is a versioned, immutable SQL file.

## File location and naming

- Path: `src/main/resources/db/migration/`
- Pattern: `V<version>__<snake_case_description>.sql`
- Two underscores between version and description.
- Use **incrementing integer versions** (`V1`, `V2`, `V3`, …) — match what's already in the directory. Never reuse or renumber.
- If teams collide on version numbers, switch the project to timestamp versions (`V20260509123000__…`); don't mix the two styles.

## Rules

1. **Never edit a migration that has been merged or applied.** Flyway checksums applied scripts; editing them breaks `validate-on-migrate`. To fix a mistake, write a new migration that corrects it.
2. **One logical change per file.** Easier to review, easier to roll forward.
3. **Idempotency is not required** — Flyway tracks `flyway_schema_history` and won't re-apply. Don't add `IF NOT EXISTS` to mask version conflicts.
4. **Use Postgres-native types**: `BIGSERIAL` / `BIGINT GENERATED BY DEFAULT AS IDENTITY` for IDs, `NUMERIC(p, s)` for money (never `FLOAT`/`DOUBLE`), `TIMESTAMP WITH TIME ZONE` for instants.
5. **Match Spring Data JDBC naming**: snake_case tables and columns. An entity `class Expense { Long id; String firstName; }` maps to table `expense`, columns `id`, `first_name`. Override with `@Table` / `@Column` only when unavoidable.
6. **Add indexes in the same migration as the table** when access patterns are already known; otherwise add them in a follow-up migration with measured justification.

## Workflow

1. Read the current migration directory to find the next version number:
   ```bash
   ls src/main/resources/db/migration/
   ```
2. Create `V<next>__<description>.sql`.
3. If touching an existing entity, update the `@Table`/`@Column`/field mappings in the same change.
4. Run the app or `./gradlew bootRun` against a real Postgres to confirm the migration applies. Flyway runs automatically on context startup.
5. For tests that hit the DB, prefer `@DataJdbcTest` against a Testcontainers Postgres so migrations run against the same engine as production. Avoid H2 — its dialect quirks defeat the point of SQL-first migrations.

## Configuration reference

In `application.yaml`:

```yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: false   # flip to true only when adopting Flyway on an existing DB
    validate-on-migrate: true
  sql:
    init:
      mode: never                # disables Spring Boot's schema.sql/data.sql so Flyway is the only source of truth
```

If you ever need to reset a local dev DB, drop and recreate the database — do not delete rows from `flyway_schema_history` to "re-run" a migration.
